# Shallow-water launch policy

The observed bug accepts the dive, applies the impulse, switches stance to prone and lowers the drowning reference from root + 1.3 to root + 0.4. Swimming consumes that submersion and cancels the dive around 10–12 ms into the action. Forcing standing immediately clears the condition again.

The policy changes the reference during a newly accepted airborne dive, rather than predicting the entire landing trajectory. It preserves the normal leap and evaluates water again at landing. The native dive landing timer becomes positive in the land_dodge path; the capture shows it changing to 0.5 at touchdown. It is not the ambiguous motion byte at offset 0x0c, which also changes while ascending.

The module resolves the current locally owned avatar through player manager, entity-owner map and avatar registry. Local index zero is not assumed. It validates the Drownable and stance records against that same entity, the resource identity, the root node, supported reference settings and native two-second dive timeout, read at its build 25480438 location with the previous location as a fallback. The loader verifies both module file hashes. The Windows adapter permits only existing private read/write data pages.

Acquisition requires a newly observed active dive, prone stance, no swimming/ragdoll, no landing timer, at most 0.05 seconds of engine dive time, an enabled non-drowned avatar and the original prone offset. The offset is leased as -1.3 instead of -0.4. When the first prone frame has already accumulated at most 0.05 seconds of submersion, that timer is reset once so the native swim predicate cannot consume the stale prone result. The remaining drown timer and all enable/state flags retain engine ownership.

The reference is restored on native landing, dive completion, another stance/state, disabled drowning, or the native two-second airborne timeout. When the secondary water predicate is enabled, surface height above the standing reference releases the lease immediately for normal deeper-water processing. When disabled, stored surface zero is ignored as a reset value. A native offset change is respected rather than repeatedly overwritten.

Restoration verifies the original entity and Drownable/stance storage identity, so it can clean up the old avatar after a player or mission transition without writing a reused record. It restores the current stance's ordinary offset: a newly standing avatar never receives stale prone bytes. Snapshot guards are checked before acquisition; these are consistency checks rather than synchronization primitives.

The two eligible writes are four bytes at the local Drownable runtime record +8 (offset) and +16 (one-time startup elapsed correction). No native calls, hooks, executable allocations, physics queries, impulse changes or global component edits are introduced. The existing shared-loader callback runs checks at both boundaries of the original Lua update and restores on shutdown or exceptions.

Offline tests exercise the production snapshot reader and writer against bounded memory with a remote avatar at index zero and local avatar at index one. A recorded stationary failure supplies the startup water/reference/timer values. Tests evaluate the native submersion predicate before and after the edit, plus dry and wet landings, deeper water, ordinary prone, swimming, ragdoll, disabled water, timeout, identity reuse, mission/player changes, coherent-snapshot rejection and failed/partial writes. Package tests verify dependency, sole resource ownership, bytecode format, artwork metadata and hashes.

The unresolved integration question is whether Lua update reliably observes the first dive frame before swimming consumes it. Polling an active dive after cancellation cannot recover the lost action, and this candidate deliberately does not replay input or manufacture a new dive. Offline fixtures prove the policy and write boundaries, not callback scheduling or multiplayer behavior.

In the first installed test, data-v1 loaded but stopped eleven seconds after process start with `Game pointer unavailable`; all five counters remained zero. The deployed resource matched the supplied build exactly. A later read-only call of the same production snapshot succeeded. The stripped error did not identify the individual pointer. These observations support an initialization-time availability failure, and definitively show that the installed v1 did not modify any dives.

data-v2 distinguishes unavailable native state from invalid data. Null pointers, empty maps, unavailable reads, missing avatar records and transient stance/movement readiness return a stage-specific waiting status; the update wrapper remains active. It still rejects nonzero invalid pointers, incompatible settings/layouts, and failed writes. Existing leases are restored when their original identities can still be verified. Regression fixtures cycle fourteen pointer locations through null to ready, then prove the same module instance can protect a later dive; the loader wrapper is separately exercised across repeated waits and recovery.

The production Lua snapshot reader also resolved a mission avatar through a read-only process handle. Separate local interoperability checks exercised Windows adapters and shared-loader resource ownership. These checks support the data layout and integration design, but do not establish successful dive behavior. Research logs and raw captures are intentionally excluded from the public source tree.

Gameplay acceptance: repeat several dives from the failing shin-depth patch onto dry land; verify normal displacement and prone landing. Also dive back into shallow water, enter deep water, try ordinary prone, and check a dry-ground dive. Inspect observed/protected/startup_clears/short_ends counters, then exercise death/reinforcement, mission exit and host/client ownership. A counter increment means the data edit occurred, not that traversal succeeded. Do not label the release gameplay-verified until those results support it.
